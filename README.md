# ЛР1. Инференс языковой модели

Главный вопрос: из чего складывается время ответа и как оно меняется под нагрузкой?
Отдельный репозиторий продолжает подход ЛР0: одна команда, чистый Git,
итоговая конфигурация, метаданные, первичные результаты и MLflow.

## Сервер

В уже настроенном Colab сервер работает отдельно на Tesla T4:

```bash
vllm serve Qwen/Qwen3-4B-Instruct-2507 --dtype half --max-model-len 32768 --gpu-memory-utilization 0.90 --max-num-seqs 32 --max-num-batched-tokens 2048 --enforce-eager --enable-prefix-caching --enable-auto-tool-choice --tool-call-parser hermes --host 127.0.0.1 --port 8000
```

Сохранить журнал в `/content/vllm.log`, команду в `/content/server_command.txt`.
При повторении использовать `--revision` из `server_passport.json`.
`enforce-eager` отключает компиляцию/CUDA graphs: результаты относятся к этому режиму.
Адрес локальный для среды Colab; при новой сессии сервер нужно запустить заново.

## Подготовка и запуск

```bash
python -m pip install mlflow==3.18.0 matplotlib
python lr1.py prepare
python lr1.py check
```

Подготовка скачивает Pride and Prejudice (Project Gutenberg №1342), создаёт
запросы, манифест, паспорт и lock-файл окружения. Загрузить эти подготовленные
файлы вместе с кодом/конфигурациями на GitHub и получить чистый Git.
Исходный текст и списки запросов восстанавливаются командой prepare по манифесту.
Зафиксировать прогноз до итоговых измерений.

```bash
python -m unittest -v test_lr1.py
python lr1.py run --experiment all --run-id lr1_final
python lr1.py analyze --run-id lr1_final
python lr1.py pack --run-id lr1_final
```

Можно выполнять отдельно: `--experiment exp1`, `cache`, `exp2`, `load`.
Продолжение того же run-id выполняет только отсутствующие записи; уже сохранённые
неуспехи не перезапускаются. Проверяются коммит, конфигурация, данные и паспорт.
Изменение условий требует нового run-id и нового заранее сохранённого прогноза.

Всего запланировано 320 измерений: 25 exp1, 3 cache, 20 exp2, 272 load.
Перед каждой группой один отдельный прогрев, не включённый в статистику.
Длины входов проверяются по `usage.prompt_tokens`, выходов — по
`usage.completion_tokens`. TPOT использует N−1, а не число фрагментов.
`results.jsonl` дописывается после каждого запроса, включая ошибки.
Отключены автоматические повторы клиента. Разные запросы изолированы cache_salt;
в тесте кеширования соль общая для трёх повторов.

Параметры генерации явно указаны в коде и endpoint.yaml: temperature=0,
top_p=1, top_k=-1, min_p=0, repetition_penalty=1, seed=0,
frequency_penalty=presence_penalty=0, ignore_eos=True.

## Результаты

`runs/<run_id>/` содержит config.yaml (JSON является допустимым YAML), metadata.json,
results.jsonl, warmup.jsonl, условия входных запросов и файлы метрик сервера.
`reports/` содержит CSV, summary.json и PNG. Анализ пересчитывает показатели
из первичных записей, сохраняет таблицы/графики в MLflow и пишет проект отчёта
`reports/report.md` с измеренными числами. Для защиты: `python lr1.py analyze`.

Ошибки сохраняются; таблицы показывают весь запланированный знаменатель,
число успехов и неуспехов. Медианы задержек подписаны как оценки среди успешных,
p90 TTFT включает неуспехи как бесконечность. Предел нагрузки считается
выполненным только при отсутствии ошибок и выполнении двух SLO.
Goodput — число успешных запросов с обоими индивидуальными пределами за секунду.

На нагрузке сохраняются метрики `/metrics` до/после и раз в секунду во время
группы, чтобы увидеть очередь, которая исчезает после завершения запросов.
Пропускная способность: суммарные наблюдённые выходные токены / интервал
от первой отправки до последнего текстового фрагмента (или конца ошибки).
При возобновлении прерванного уровня суммируются активные интервалы сегментов;
это явно отмечается в CSV и отчёте.

Артефакты и базы не входят в Git. ZIP сдаётся отдельно. Весов модели в архиве нет.
Код подготовлен с ИИ; арифметика, квантили, знаменатели, длины и кеш проверены
тестами/проверками. Реальные выводы формируются только после выполнения на GPU.
