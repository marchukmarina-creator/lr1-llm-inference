## Короткий запуск на защите

Рядом с кодом распаковать сохранённые runs/, data/ и mlflow.db/mlruns/.
При объединении сохранить новый код и итоговый reports/report.md.

    python lr1.py analyze --run-id lr1_final

Это пересчитает таблицы и графики из первичных записей, проверит их и
сохранит итоговый Markdown-отчёт в MLflow. Модель для анализа не нужна.

Самостоятельная проверка и пересоздание текста:

    python finalize_report.py --source . --output reports

PDF (отдельная необязательная зависимость):

    python -m pip install -r requirements-report.txt
    python finalize_report.py --source . --output reports --pdf

Скрипт отчёта сверяет длины usage, N-1, времена фрагментов, хеши входов,
знаменатели таблиц, прогревы и одинаковый текст трёх запросов проверки кеша.

## Как найти исходные графики MLflow

lr1 -> lr1_final -> дочерние exp1_*, exp2_*, load_*: интерактивные метрики.
В исходном архиве PNG находятся в эксперименте Default -> analysis ->
Artifacts -> reports/figures. Это особенность исходной регистрации анализа;
на значения экспериментов не влияет. После короткого запуска новой версии
analyze графики и окончательный report.md появляются в lr1 -> analysis.

## Главный вывод

Наибольшая проверенная нагрузка, выполняющая заранее заданные пределы, — два
клиента (p90 TTFT≤2 с и медиана TPOT≤100 мс).
При четырёх клиентах уже нарушен TTFT, хотя KV занят примерно на 12%.
Поэтому раннее ухудшение связано не с исчерпанием памяти кеша.
При 32 клиентах кеш занят примерно на 96%, а throughput вышел на насыщение.
Результат относится к Tesla T4 и enforce-eager, не ко всем серверам vLLM.
